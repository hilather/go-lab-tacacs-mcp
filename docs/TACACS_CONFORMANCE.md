# TACACS+ Conformance and Completeness Matrix

Status: release-blocking checklist  
Normative baseline: RFC 8907 and RFC 9887  
Last updated: 2026-08-13

## 1. Purpose

This file defines what “complete TACACS+ support” means for TacLab. It is both an implementation checklist and the required evidence index for release review.

No agent may mark a row complete based only on source inspection or a third-party library claim. Completion requires an automated test, a linked fixture or interoperability case, and the documented behavior in operator references.

## 2. Status rules

Use these status values in generated conformance output:

| Status | Meaning |
|---|---|
| `NOT_STARTED` | No implementation evidence |
| `IN_PROGRESS` | Implementation exists but required evidence is incomplete |
| `PASS` | Automated conformance evidence passes |
| `N/A_RFC_DEPRECATED` | The current RFC directs implementations away from the option; explicit rejection behavior is tested |
| `DEFERRED_MAY` | Optional `MAY` feature deferred through an ADR |
| `DISPOSITIONED_SHOULD` | `SHOULD` not implemented; approved ADR documents why and interoperability impact |
| `FAIL` | Known nonconformance; release blocker when normative level is MUST/MUST NOT |

Release rules:

- Every RFC `MUST` and `MUST NOT` row must be `PASS` or an exact deprecation disposition explicitly allowed by the RFC.
- Every RFC `SHOULD` or `SHOULD NOT` row must be `PASS` or `DISPOSITIONED_SHOULD` with an ADR.
- Every `PROJECT MUST` row is also release blocking. These rows deliberately elevate an RFC-defined option that a generic server may omit because TacLab promises complete lab coverage.
- Every supported `MAY` option must have tests. Deferred optional features must be visible and must not be advertised.
- A parser-recognized but unsupported option must receive the correct failure/error and session disposition.

Level labels are interpreted as follows:

| Level | Meaning |
|---|---|
| `MUST`, `MUST NOT`, `SHOULD`, `SHOULD NOT`, `MAY` | Normative requirement applicable to the TACACS+ server role in the cited RFC |
| `PROJECT MUST` | TacLab 1.0 release requirement added to provide the promised complete lab feature set |
| `PROJECT` | Project quality, determinism, security, or operability requirement |
| `OPERATOR MUST/SHOULD` | Deployment requirement or warning that must be represented in validation/documentation/evidence |
| `CLIENT-ROLE` | Normative statement applies to a TACACS+ client; tracked for the independent test client and interoperability, not claimed as server behavior |
| `Removed` or `Deprecated` | Legacy behavior must not be advertised; rejection or safe disposition is tested |

### 2.1 Machine-readable registry

Row IDs are encoded in `testdata/conformance/rfc8907.yaml` and `testdata/conformance/rfc9887.yaml`. 1.0 qualification fills status and evidence in the YAML; `make generate` rewrites this inventory. `make generate` writes [docs/generated/conformance.md](https://github.com/hilather/go-lab-tacacs-mcp/blob/main/docs/generated/conformance.md). `make check-registries` fails on duplicate IDs, empty tables, and contract rows that are missing from the YAML. RADIUS/PRJ rows live in sibling YAML files and [docs/RADIUS_CONFORMANCE.md](https://github.com/hilather/go-lab-tacacs-mcp/blob/main/docs/RADIUS_CONFORMANCE.md); they are not TACACS 1.0 `-release` gates.

Do not mark a row `PASS` without linked evidence. `make check-registries` includes the 1.0 MUST/SHOULD `-release` gate (mandatory rows `PASS` or `N/A_RFC_DEPRECATED`; SHOULD rows `PASS` or `DISPOSITIONED_SHOULD`; evidence prefixes and resolvable `Test*`/`Fuzz*`/`Benchmark*` symbols). Structural-only validation is `go run ./tools/check-registries` without `-release`.

## 3. Test evidence conventions

Each completed row must identify one or more of:

- `unit:` package test.
- `golden:` independent packet fixture.
- `fuzz:` fuzz target/corpus.
- `interop:` external client/server or physical/virtual device case.
- `race:` concurrent single-connect case.
- `bench:` relevant performance benchmark.
- `docs:` operator/configuration documentation.

Tests generated by a TacLab client using the same codec are not sufficient as the only evidence.

### 3.1 Server and client role scope

TacLab is a TACACS+ server. Server-applicable RFC requirements are release gates. Client-only normative statements are tracked where they affect the independent test client, interoperability harness, downgrade testing, or interpretation of server replies; they must not be misrepresented as server features. Operator requirements are satisfied through safe defaults, configuration validation, warnings, deployment documentation, and executable lab evidence.
