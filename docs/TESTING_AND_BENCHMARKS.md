# Testing, Regression, Fuzzing, and Performance Policy

Status: mandatory  
Last updated: 2026-08-12

## 1. Purpose

TacLab processes authentication credentials, authorization decisions, untrusted binary packets, and concurrent network sessions. Tests are part of the product contract. The project does not accept protocol behavior, bug fixes, or performance-sensitive changes without durable automated evidence.

## 2. Core policy

- Every defect gets a regression test that fails before the fix.
- Every feature gets positive, negative, boundary, and authorization tests.
- Every TACACS parser/state-machine defect adds a fuzz seed.
- Every hot-path change adds or updates a benchmark.
- Every REST capability has MCP parity tests unless explicitly protocol-only.
- Every concurrency change runs under the Go race detector.
- Documentation and generated schemas are checked for drift.
- Internal client/server tests that share the same codec are never the sole protocol evidence.

## 3. Test layers

### 3.1 Pure unit tests

Cover:

- packet field encoding and decoding.
- AV-pair parsing and validation.
- credential algorithms using independent published vectors.
- client match precedence.
- username normalization.
- rule matching and deterministic order.
- overlay merge/tombstone semantics.
- token hashing and scope checks.
- cursor and revision behavior.
- common error mapping.
- operation registry completeness against `api/operations.yaml` (every ID registered; status/build/policy.evaluate against a real snapshot).
- REST/MCP parity for `system.status.get` and `policy.evaluate` (same operation registry; adapters never call each other).
- Full REST/MCP/direct equivalence in `internal/api/parity` for every `PARITY_REQUIRED` operation (P11.5).
- ASCII LOGIN + PAP + CHAP + ENABLE (type ignored) + one service rule + one command rule + accounting START through the legacy listener (`cmd/taclabd` e2e).

Unit tests must be deterministic and use injectable clocks/random sources.

### 3.2 Golden protocol fixtures

Store raw binary fixtures under `testdata/protocol`. Each fixture has metadata describing:

- source or independent construction method.
- transport.
- shared secret when required, stored only as a non-production test value.
- header fields.
- expected decoded fields.
- expected reply/status.
- expected connection disposition.
- RFC section.

Required fixture classes:

- each authentication request/reply/continue flow.
- authorization request and PASS_ADD/PASS_REPL/FAIL/ERROR replies.
- every valid and invalid accounting flag combination.
- single-connect negotiation.
- wrong secret and body-length mismatch.
- sequence boundary and wrong parity.
- cleartext legacy packet rejection.
- TLS flag behavior.
- maximum and empty fields.
- duplicate/ordered AV pairs and values with separators.

Golden fixtures should be generated by an independent script or captured from an external implementation, then reviewed and committed as bytes. A generator may be checked in, but tests consume fixed fixtures.

### 3.3 Domain integration tests

Exercise real state, policy, credential, and event services without network adapters:

- authentication against config and runtime users.
- override and tombstone behavior.
- config reload/rebase.
- command authorization and explanation trace.
- accounting acceptance and ring overwrite.
- token creation/revocation.
- revision conflicts.
- secret-redacted exports.
- legacy shared-secret minimum-complexity enforcement, 32-plus-character support, process-local keyed-HMAC reuse detection, and lifecycle status with an injected clock.

### 3.4 Connection/state-machine tests

Use real TCP connections or `net.Pipe` where appropriate. Cover:

- fragmented headers and bodies.
- read/write timeout.
- client disconnect at every authentication step.
- abort handling.
- non-single-connect close behavior.
- concurrent single-connect sessions.
- duplicate session IDs.
- packet reordering.
- late packets after session completion.
- connection-level secret failure while other sessions exist.
- graceful shutdown and drain.
- per-client/global limit enforcement.

Run representative tests with `-race` and repeated execution.

REST middleware overhead is `BenchmarkMiddlewareOverhead` / `BenchmarkStatus` in `internal/api/rest`.

### 3.5 REST contract tests

Start the real HTTP adapter over an in-memory listener. Validate:

- OpenAPI-conformant requests/responses.
- strict JSON decoding.
- authentication and every relevant scope set.
- pagination/cursors.
- revision and idempotency behavior.
- problem-detail error mappings.
- body-size limits.
- session-cookie/CSRF behavior.
- SSE reconnect, heartbeat, reset, filtering, and slow-subscriber handling.
- secret omission and safe errors.

### 3.6 MCP contract tests

Use the official SDK client (`TestOfficialSDKClient`) plus in-tree Streamable HTTP contract tests ([ADR 0011](https://github.com/hilather/go-lab-tacacs-mcp/blob/main/docs/decisions/0011-mcp-thin-adapter-go-124.md)). Validate:

- Streamable HTTP behavior for the pinned specification.
- tool and resource discovery.
- deterministic tool ordering.
- scope-filtered discovery.
- input/output schema validation.
- structured content.
- common errors.
- resource reads.
- event/resource subscriptions.
- per-request authorization.
- malformed JSON-RPC and unsupported method behavior through the SDK.

Use MCP Inspector for exploratory debugging, not as the only automated evidence.

### 3.7 REST/MCP parity tests

Follow `API_PARITY.md`. `internal/api/parity` runs every `PARITY_REQUIRED` operation through the registry, REST, and MCP against isolated identical fixtures. Compare domain result, state revision, events, errors, and redaction. `events.subscribe` is compared at domain-event level (REST SSE bodies versus MCP URI notify plus `events.list`), not wire identity.

### 3.8 Frontend tests

#### Unit/component

- generated-client integration wrappers.
- source badges.
- validation/error summaries.
- revision conflict rendering.
- one-time token display and clearing.
- event stream reducer/reconnect behavior.
- accessible destructive confirmation.

PR-19a/19b ship Playwright keyboard smokes (`npm --prefix web run test:e2e`) plus Vitest tests for login, source badges, status, revision conflicts, one-time tokens, events reconnect, auth-test password clearing, policy explain, and confirmed runtime reset. Full lab-service workflows below wait on the PR-21 topology.

#### End-to-end

Use a real TacLab service in a disposable environment. Required workflows:

- sign in with configured token.
- view status/listeners.
- create runtime user/group/client.
- update a configured object and observe `OVERRIDE`.
- tombstone and restore configured object.
- run authentication test.
- run policy explanation.
- view live event.
- create token and confirm one-time value.
- reload valid/invalid config.
- reset runtime state.
- restart and verify runtime objects disappear.

Run keyboard-only smoke coverage and automated accessibility checks. Automated tools do not replace manual release review for focus order and understandable labels.

### 3.9 Container integration tests

`make lab-test` builds `ghcr.io/hilather/go-lab-tacacs-mcp`, runs `tools/labgen` into a temporary directory, and starts `deployments/compose/compose.yaml` plus `compose.lab-test.yaml` under a unique project name. Verify:

- non-root UID.
- read-only root filesystem.
- secret files readable only by the service user.
- no secret embedded in image history or layers.
- legacy port mapping.
- secure port mapping and mTLS.
- UI/REST/MCP access.
- health/readiness.
- reload signal.
- graceful stop.
- restart baseline reset.
- no required persistence volume.
- SSE / MCP listen subscriber survives longer than `listeners.http.write_timeout` (`LAB-SSE-001`; unit coverage in `internal/api/rest` and `internal/api/mcp`).
- Source-IP disposition is recorded (`LAB-SOURCE-001`, LAB_DEPLOYMENT §4.3). File-watch reload remains off.

### 3.10 Interoperability tests

Maintain a versioned matrix with:

- external TACACS client/server implementation version.
- network device platform and software release.
- transport.
- authentication types.
- authorization form.
- accounting form.
- single-connect behavior.
- observed vendor-specific AV pairs.

At least one external implementation and two device families are required for the 1.0 release when lab equipment is available. Automated internal conformance remains required even when a device does not expose a feature.

## 4. Regression-test workflow

For every bug:

1. Capture the smallest safe reproduction.
2. Add a test named for behavior, not ticket number alone.
3. Confirm it fails on the parent revision for the intended reason.
4. Fix the implementation.
5. Add adjacent boundary/negative cases.
6. Add fuzz seed when binary/config parsing or state transition is involved.
7. Update conformance row and documentation.
8. Run relevant benchmarks and compare.

Regression tests are permanent. Removing one requires an ADR-quality explanation or replacement proving equal or stronger coverage.

## 5. Fuzzing

### 5.1 Required Go fuzz targets

- header decode.
- every packet-body decoder.
- body-length reconciliation.
- legacy obfuscation/de-obfuscation.
- AV-pair parser.
- username/text validation.
- authentication session transition function.
- connection sequence/session dispatch model.
- configuration decoder/compiler (`FuzzParse`).
- cursor decoder (`FuzzDecodeCursor`).
- common API request validators for complex policy rules (`FuzzEvaluatePolicyRequest`).
- remaining packet-family bodies (`FuzzAuthenContinue`, `FuzzAuthenReply`, `FuzzAuthorResponse`, `FuzzAcctReply`).
- AV-pair parser (`FuzzParseAVPair`, `FuzzParseArgument`).
- username PRECIS (`FuzzCanonicalUsername`).

### 5.2 Fuzz invariants

- no panic.
- no out-of-bound read/write.
- no allocation beyond configured/test bound.
- deterministic result for the same input.
- encode(decode(x)) consistency for accepted canonical packets.
- rejected packets produce a typed safe error.
- no secret content enters error strings.
- state machine never accepts an impossible sequence.
- parser completes within a bounded time.

### 5.3 Execution cadence

Every change:

- run seed corpora as normal tests.
- run a short fuzz smoke job on primary targets.

Scheduled/release:

- run each target for a configured extended duration.
- preserve new crashing inputs.
- publish execution counts and unique corpus changes.
- optionally integrate with OSS-Fuzz when repository visibility and packaging allow.

## 6. Race, deadlock, and leak testing

Required:

```bash
go test -race ./...
```

Additional stress cases:

- concurrent state readers during repeated overlay writes/reloads.
- single-connect sessions entering and leaving concurrently.
- event subscribers connecting/disconnecting while accounting arrives.
- token revocation during API calls.
- shutdown during authentication continuation.
- reload during active session.
- slow writer/reader.

Use goroutine leak checks around server lifecycle tests. All waits have deadlines. Tests must not use arbitrary long sleeps when channels, fake clocks, or eventual assertions can prove state.

## 7. Security-negative tests

### 7.1 Secret canaries

Give every secret class a unique canary and scan:

- logs.
- errors.
- events.
- traces/test exporters.
- REST outputs.
- MCP outputs.
- OpenAPI examples.
- config exports.
- UI DOM snapshots.
- generated docs.
- crash/panic output.

Only the one-time newly created token response may contain its token canary.

For legacy shared secrets, additionally verify that reuse detection can identify equal values without exposing a fingerprint; weak/short validation errors never echo the candidate; lifecycle warnings contain only client IDs and non-secret dates/status; and secret rotation followed by atomic reload updates the process-local comparison state and lifecycle status without leaking either old or new material.

### 7.2 Authorization matrix

For every operation:

- no token.
- malformed token.
- unknown token.
- expired token.
- revoked token.
- exact required scope.
- missing one required scope.
- additional unrelated scopes.
- browser cookie without CSRF token on mutation.

### 7.3 Protocol adversarial cases

- oversized length.
- length overflow/underflow.
- unexpected control characters.
- invalid enum values.
- wrong minor version for flow.
- repeated prompts beyond limit.
- wrong challenge lengths.
- unexpected body data.
- duplicate session IDs.
- invalid shared-secret transform result.
- shared-secret lengths below policy, at 16, at 32, and above 32 characters.
- shared-secret reuse warning enabled/disabled and deduplication behavior.
- rotation status boundaries immediately before, at, and after warning/due timestamps.
- cleartext legacy body.
- TLS version downgrade.
- missing/invalid client certificate.
- TLS packet missing required unencrypted flag.
- attempted early data.
- independent testclient TLS role (not shared-codec loopback): immediate handshake, no legacy fallback, DNS-ID/IP-ID/SRV-ID (URI-ID unused), UNENCRYPTED on every packet, ClientHello without `early_data`.

## 8. Benchmark policy

### 8.1 When a benchmark is mandatory

Add/update benchmarks for changes to:

- packet codec.
- obfuscation.
- challenge-response algorithms.
- client lookup.
- policy compilation/evaluation.
- snapshot merge/publication.
- token verification (`internal/api/auth` `BenchmarkVerifyBearer`, `BenchmarkAuthenticateToken`).
- event append/read/fanout.
- list/pagination serialization.
- SSE/MCP event distribution.
- large React list/event rendering or reducer paths.

### 8.2 Benchmark fixtures

Keep deterministic generated fixtures:

| Size | Users | Groups | Clients | Rules | Event ring |
|---|---:|---:|---:|---:|---:|
| Small | 100 | 10 | 20 | 100 | 1,000 |
| Medium | 10,000 | 100 | 500 | 5,000 | 10,000 |
| Large | 100,000 | 500 | 5,000 | 25,000 | 100,000 |

Large fixtures are for scheduled/release jobs when ordinary CI runtime is excessive.

### 8.3 Required Go benchmarks

Suggested names:

```text

BenchmarkAuthenticationStartDecode
BenchmarkAuthorizationDecode
BenchmarkAccountingDecode

BenchmarkLegacyObfuscate_1KiB
```

Report `-benchmem`.

`make bench` succeeds when `Benchmark*` functions exist under `internal/tacacs`, `internal/policy`, `internal/state`, or `internal/aaa`. Header decode/encode, `BenchmarkLegacyObfuscate_64B` / `BenchmarkLegacyObfuscate_1KiB`, `BenchmarkAuthenStartDecode`, and `BenchmarkAuthorDecode_16Args` / `BenchmarkAuthorDecode_255Args` live under `internal/tacacs/codec`. `BenchmarkCHAPLogin` is the AAA dispatch bench (no Argon2id). `BenchmarkFullHandshake`, `BenchmarkResumedHandshake`, and `BenchmarkPostHandshakeAuthor` live under `internal/tacacs/tls`. Header/obfuscation benches under `tools/spike` are evaluation-only.

### 8.4 Credential benchmarks

Password verification is intentionally expensive and has separate benchmarks under `internal/credentials` (not `make bench`):

- `BenchmarkArgon2idVerify` — ADR-0002 `DefaultParams` (64 MiB, t=3, p=1) on reference hardware.
- `BenchmarkArgon2idVerifyParallel` — concurrent verification at the KDF worker cap (default 2).
- `BenchmarkCHAPVerify`, `BenchmarkMSCHAPv1Verify`, `BenchmarkMSCHAPv2Verify`.

Do not reduce password KDF strength merely to pass general API latency budgets. Configuration validation should warn when parameters are outside project security guidance. See [ADR 0002](https://github.com/hilather/go-lab-tacacs-mcp/blob/main/docs/decisions/0002-password-kdf.md).

### 8.5 Frontend performance tests

Measure:

- production bundle size.
- initial dashboard render.
- 10,000-row virtualized event list behavior.
- event burst reducer throughput.
- memory after sustained event streaming.
- no unnecessary whole-application rerenders from one event.

Budget changes are reviewed with bundle analyzer and browser trace evidence.

## 9. Performance regression rules

Compare on the same runner class using multiple samples and `benchstat` or equivalent.

A change requires explicit review when it causes any of:

- greater than 10 percent statistically meaningful latency regression in a stable benchmark.
- greater than 15 percent allocation or bytes-per-operation regression.
- a new allocation on a previously allocation-free header/hot lookup path.
- increased lock contention visible in mutex/block profiles.
- unbounded memory, goroutine, connection, queue, or subscriber growth.
- materially increased UI bundle size without user benefit.

An approved regression must include cause, measured impact, alternatives, and updated budget/ADR when permanent.

## 10. Release load profiles

Absolute numbers are frozen in [`benchmarks/budgets.yaml`](https://github.com/hilather/go-lab-tacacs-mcp/blob/main/benchmarks/budgets.yaml) (2026-08-13, Intel i7-8750H, Go 1.24.5). The 10-minute 250-connection soak is an **operator procedure** and was not executed in the 1.0 qualification environment; CI uses saturation, leak, and race tests. The initial release suite must include these shapes:

### 10.1 Authorization/accounting profile

- 250 concurrent client connections.
- mix of single-connect and one-session connections.
- 80 percent authorization, 20 percent accounting.
- small and medium policy fixtures.
- sustained 10 minutes.
- no unexpected failures, races, or unbounded growth.
- p95/p99 and throughput captured.

### 10.2 Authentication profile

- bounded concurrency appropriate to the configured password KDF worker limit.
- separate ASCII/PAP and challenge-response runs.
- prove overload rejection/backpressure rather than memory growth.
- capture queue delay separately from credential verification time.

### 10.3 Admin/event profile

- repeated list/read operations on medium state.
- 25 live REST SSE subscribers and representative MCP subscribers.
- event burst plus concurrent state mutations.
- slow-subscriber reset/disconnect behavior.

The goal is reproducible lab capacity, not a misleading universal throughput claim.

## 11. Profiles and diagnostics on regression

Capture as appropriate:

- CPU profile.
- heap profile.
- allocation profile.
- mutex profile.
- block profile.
- goroutine dump.
- execution trace.
- browser performance trace.
- network packet capture with secrets protected.

Do not commit captures containing credentials or token values.

## 13. Flaky-test policy

Flaky tests are defects.

- Do not silently retry as the only fix.
- Quarantine requires a linked task, owner, reason, and expiration date.
- A quarantined security, conformance, parity, or race test blocks release.
- Fix clock, ordering, ports, or resource cleanup rather than increasing sleeps.

## 14. Coverage use

Coverage percentage is diagnostic, not the sole quality gate. Require coverage of behaviors and branches that affect:

- all protocol statuses and invalid options.
- every parity-required operation.
- every scope decision.
- every overlay transition.
- secret redaction.
- error/session disposition.

Track package coverage trends and investigate material drops.

## 15. Documentation and evidence outputs

Tests should generate or feed:

- conformance report (`docs/generated/conformance.md` from the YAML registries).
- parity report (`docs/generated/api-parity.md` from `api/operations.yaml`).
- benchmark report.
- interoperability matrix.
- build/spec version report.

CI must fail if generated reports differ from checked-in release metadata where the repository policy requires checked-in outputs.
